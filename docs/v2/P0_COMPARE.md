# 시범판 A · B 비교 (P0) — 심판 보고

2026-11-17. 같은 구간(`docs/v2/SLICE0.md`)을 두 화면 방식으로 만든 시범판을 **같은 방법으로** 돌려 보고 적은 문서다.
숫자는 모두 헤드리스 Chromium(소프트웨어 렌더러)에서 잰 것이라 **실제 폴드의 속도가 아니다**. 마지막 판단은 소유자가 폴드에서 직접 해 보고 내린다.

- 들어가는 곳: 타이틀 메뉴 맨 아래 **리빌드 시범** → 시범판 A / 시범판 B / 돌아가기 (`src/v2/chooser.js`). 주소로 바로: `index.html?scene=v2a`, `?scene=v2b`.
- 비교 그림 8장 (왼쪽 A, 오른쪽 B, 폴드 화면·화질 높음): `/tmp/claude-0/v2/fold/compare/1_street.png` … `8_yard_fight.png`
- 검사 도구: `node tools/v2/p0_referee.mjs` (두 시범판 공통 검사), `node tools/v2/p0_entry_check.mjs` (타이틀 줄·고르기 화면), 만든 쪽의 `tools/v2/proto_a_check.mjs` · `proto_b_check.mjs`.

## 2. 보기에 어떤가 (비교 그림을 직접 보고 적음)

**A**
- 거리(횡): 바닥이 원근으로 멀어지지만 건물은 납작한 정면 그림이다. v1 에 "깊이 있는 바닥"이 생긴 정도로 보인다. 창·문은 코드로 그린 네모라 가장 허전하다.
- 골목(종): 가장 잘 나온 곳. 벽이 소실점으로 모이고 횃불이 줄지어 멀어져 "안으로 들어간다"는 느낌이 분명하다.
- 마당: 다시 평평해 보인다. 벽이 낮고 카메라가 돌지 않아서다.
- 구덩이: 바닥의 어두운 네모로만 보여 구덩이인지 알기 어렵다.
- 폴드(세로가 긴 화면)에서는 거리 구간 아래쪽 1/4 쯤이 빈 어두운 바닥이다.

**B**
- 거리부터 "작은 입체 모형 속"처럼 보인다. 지붕, 벽 두께, 단상 옆면, 구덩이 속 벽이 실제로 있다.
- 모퉁이에서 카메라가 돌아 골목을 길이 방향으로 내려다본다. 골목·마당에서 캐릭터가 A 보다 크게 보인다.
- 단점: 앞쪽 가로등·상자가 영웅을 가리는 순간이 있다(단상 위 장면에서 가로등 불빛이 영웅 위에 겹침). 골목 왼쪽 벽에 붙어 걸으면 벽이 화면 왼쪽 절반을 덮는다(`b_wall_fills_screen.png`). 카메라 가까이 있는 적은 화면 아래 가상 패드 밑에 깔린다.
- 세계가 아직 상자 위주이고 타일이 가까이서 흐릿하다. 계단 현상(안티에일리어싱 없음)이 있다.

**둘 다 같은 점:** 캐릭터가 옆모습 한 장이라 골목 안쪽으로 걸을 때도 옆을 본다. 방식과 무관하게 재디자인에서 앞·뒤 그림이 필요하다.

## 6. 권고

**권고: B 를 뼈대로 하고 A 의 부품을 옮기는 혼합 — 이름 "B 세계 + A 규칙".** 단, 아래 "폴드 확인"을 통과할 때만.

- B 에서 가져갈 것: WebGL 세계, 깊이 버퍼 가림, 구간별 카메라, 구운 빛.
- A 에서 가져갈 것: 저작 낱말과 `stage.validate()`(바닥 겹침·닿을 수 있는가), 일시정지 화면, 조준 도움 값의 출발점, 터치 봇 검사.
- 까닭: 비교 그림 8장 모두에서 B 가 "입체 세계"로 읽히고, A 는 골목 한 곳만 그렇다. 여러 달을 들이는 리빌드에서 거리·마당이 v1 과 비슷해 보이면 리빌드의 뜻이 약해진다. B 의 약점(가림·벽 붙기·일시정지·판정 비대칭)은 값과 규칙을 고치면 되는 것들이고, A 의 약점(카메라가 못 돈다, 빛이 가짜다)은 방식 자체의 한계다.

**폴드 확인 (소유자가 10분):** 타이틀 → 리빌드 시범 → B. 맨 아래 작은 글자 줄의 fps 가 55 이상인가. 그 줄을 눌러 방식을 바꿔도 그런가. 앱을 뒤로 보냈다가 돌아와도 화면이 살아나는가. 셋 중 하나라도 안 되면 A 로 간다.

**이 권고에 대한 가장 센 반론:** B 의 속도는 아직 추측이다. 헤드리스에서는 B 가 A 보다 느리게 나왔고, 실제 기기 값은 아무도 모른다. 그리고 B 는 스테이지 한 장이 A 의 4–5배 시간(20분 대 1.5시간)이 들고 건물 조각·편집 도구를 먼저 만들어야 한다. 60장 이상을 만들 계획이면 이 차이가 달 단위로 쌓인다. A 의 골목은 이미 충분히 입체로 보이므로, "건물 정면을 채색 원화로 바꾼 A"가 더 빨리, 더 안전하게 끝난다는 주장은 틀리지 않다. 소유자가 폴드에서 A 의 거리 구간을 보고 "이 정도면 된다"고 느낀다면 A 가 맞는 선택이다.

## 8. 만든 쪽 검사 스크립트는 진짜인가

- `proto_a_check.mjs`: 진짜다. 스틱·단추는 실제 터치 이벤트로, 끝까지 가기는 가상 패드와 같은 입구(`input.touch.axis`)로 봇이 한다. 계단·상자·구덩이·깊이 판정·쓰러짐을 각각 값으로 확인한다. 프레임 시간도 JS 값과 래스터 포함 값을 따로 적는다.
- `proto_b_check.mjs`: 진짜다. 다만 끝까지 가는 봇이 **키 입력과 같은 길**(`setAutoSource`, 8방향)로 움직여서, 터치 스틱의 8방향 붙기·죽은 구역은 이 검사에 걸리지 않았다. 터치는 짧은 확인(스틱 한 번, 단추 세 개)뿐이었다. 규칙 검사(맞음·빗나감·구덩이·계단·대시·쓰러짐), WebGL 없음, 화면 되살리기, 나가기 정리는 실제로 확인한다.
- 두 스크립트 모두 심판이 고친 뒤 다시 돌려 통과했다(결과는 보고서).
