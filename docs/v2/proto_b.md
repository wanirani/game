## 0. 한눈에

- 세계(바닥·단상·계단·벽·기둥)는 **진짜 3D 저폴리 메시**이고, 원근 카메라로 그린다. 캐릭터·소품은 **세워 둔 2D 그림**이다.

- v1 셸(게임 루프·입력·가상 패드·해상도·소리·HUD 글자·토스트·페이드)은 그대로 쓴다. 고친 v1 파일은 없다.

## 1. 세계 모델과 저작 형식 — "상자 세계"

스테이지는 **축에 맞춘 상자들의 목록**이다. 한 줄이 한 덩어리이고, `world.js compileStage` 가 충돌과 그림을 **같은 데이터에서** 만든다(충돌과 그림이 어긋날 수 없다).

```js
// stage_slice0.js (발췌) — 단위 = 논리 px, x 오른쪽 · z 화면 안쪽 · y 위
parts: [
  { t: 'floor',  x: -60, z: 0, w: 1860, d: 260, mat: 'cobble' },            // 바닥 판 (윗면 y=0). 판이 없는 곳 = 구덩이
  { t: 'block',  x: 900, z: 130, w: 300, d: 120, h: 72, mat: 'stone' },      // 밟을 수 있는 상자 (단상·나무 상자)
  { t: 'stairs', x: 804, z: 150, w: 96, d: 84, h: 72, dir: 'x+', steps: 6 }, // 계단 (칸마다 상자 하나)
  { t: 'wall',   x: 440, z: 260, w: 470, d: 90, h: 350, mat: 'plaster' },    // 건물·담 (위에 설 수 없다)
  { t: 'pillar', x: 700, z: 110, r: 24, h: 236 },                            // 8각 기둥
  { t: 'roof',   x: 440, z: 260, w: 470, d: 90, y: 350, h: 70 },             // 맞배지붕 (경사면 + 박공 + 처마)
  { t: 'blocker',x: -60, z: -60, w: 2540, d: 60 },                           // 보이지 않는 벽
  { t: 'prop',   img: 'deco_village_lamppost', x: 430, z: 150, h: 196, solid: 9, light: {...}, glow: {...} },  // 그림 소품(빌보드) + 빛
  { t: 'window', x: 150, z: 259, y: 120 },                                   // 불 켜진 창 + 빛
],
sections: [ { id: 'street', label: '거리', x0, x1, z0, z1, cam: { yaw, pitch, dist, lookY, leadX, leadZ, minX, maxX, … } }, … ],
spawns:   [ { kind: 'melee', x: 640, z: 150 }, { kind: 'ranged', x: 1310, z: 216 }, { …, yard: true } ],
start, goal, sky: { img, crop, span, bottom }, fog: { color, near, far, max }, light: { ambient, moon, moonDir },
```

- **컴파일 결과**
  - `boxes` — 충돌 상자 `{x0,x1,z0,z1,y0,y1, solid, walk}`. 시범 구간: part 84줄 → 상자 73개.
  - `mesh` — 재질(텍스처)별 삼각형. 카메라는 늘 +z 쪽을 보므로 상자의 뒷면·밑면은 만들지 않는다. 면은 64 단위 격자로 쪼개 **꼭짓점마다 빛을 굽는다**(달빛 방향광 + 주변광 + 가로등·창·화로 점광 22개, 벽 밑동 어둡게, 땅 아래로 갈수록 어둡게). 실행 중 빛 계산은 0.
  - `sprites` — 소품 빌보드·빛 번짐·창. `lights` — 캐릭터 색조에도 같은 함수(`lightAt`)를 쓴다.
- **자동 검증** `validateStage(stage)` (node 에서 0.1초): 형식·재질 이름, 계단 한 칸 높이 ≤ 걸어 오르는 턱, 시작·적 위치 아래에 바닥이 있는지, **시작 위치에서 걷기+점프로 모든 적·모든 구간·goal 에 닿는지**(20 단위 격자 넓이 우선 탐색, 점프 높이 100, 벽 속 칸 제외). 실제로 이 검증이 저작 중 "소품 충돌 상자에 묻힌 적"을 하나 잡았다.
- **왜 이 모델인가**: 한 줄 = 눈에 보이는 한 덩어리라 손으로 빨리 쓰고, 도구(격자 편집기)로 만들기도 쉽고, 충돌·그림·검증이 한 데이터에서 나온다. 경사면·곡면은 없다(계단과 상자만) — 60장 이상을 찍어내는 속도를 위해 일부러 좁게 잡았다. 필요해지면 part 종류를 더한다(`ramp`, `arch`, `fence`, 높이가 다른 바닥 조각 등 — compile 한 곳만 고친다).

## 2. 카메라와 투영

- 원근 투영, 초점 거리 880 논리 px(세로로 긴 화면은 최대 +10 %): 카메라에서 880 떨어진 곳이 1 단위 = 1 px. 폴드(960×726)의 수직 시야각은 약 41°, 휴대폰(1110×540)은 34°.
- 세로로 긴 화면(폴드)은 남는 높이를 앞바닥이 아니라 벽·지붕·하늘 쪽에 쓰도록 보는 점을 위로 올린다(구간별 `tallK`).
- 구간마다 카메라 틀(`sections[].cam`)이 있고, 영웅이 구간을 넘으면 값을 지수 보간(약 1초)으로 옮긴다 → **모퉁이에서 카메라가 돌아 들어간다**.

| 구간 | 요 | 내려보는 각 | 거리 | 특징 |
|---|---|---|---|---|
| 거리(횡) | +12° (+보는 쪽 ±2°) | 20° | 790 | 길이 오른쪽 안쪽으로 물러나 보인다. 영웅 앞쪽을 90 미리 본다. 깊이는 55 % 만 따라간다 |
| 모퉁이 | 1° | 17° | 800 | 골목 어귀 앞에서 골목 안쪽이 보이도록 미리 돈다 |
| 골목(종) | 0° (±3°) | 13.5° | 660 | 낮고 가깝게: 길을 따라 내려다본다. 170 앞을 본다. 카메라 x 는 골목 안으로 묶는다 |
| 마당 | 0° (카메라 x 묶음 → 영웅을 따라 ±20° 돌아본다) | 29° | 900 | 높이 올라가 마당 전체를 본다. 마당 중심 쪽으로 30 % 끌어당긴다 |

- 조작은 세계 축 기준(오른쪽 = +x, 위 = +z). 요가 작아서(≤ 12°, 마당에서만 최대 20°) 화면 방향과 거의 같다.
- 점프 중에는 카메라가 높이를 따라가지 않는다(멀미 방지). 흔들림은 카메라 위치에 준다.
- 벽 속으로 카메라가 들어가지 않게 구간별 `minX/maxX` 로 묶고, 뒷면 제거(back-face culling)로 카메라를 향하지 않는 면은 그리지 않는다. 마당 남쪽·골목 끝의 담은 낮게 지어 카메라가 넘겨다본다(저작 규칙 두 가지: **카메라와 놀이 공간 사이에는 카메라보다 높은 벽을 두지 않는다**, **카메라가 지나는 길 위에는 카메라보다 낮은 구조물(아치·들보)을 두지 않는다** — 시범 구간에서 아치 하나가 화면 위쪽을 통째로 가려 지웠다. 둘 다 검증 항목으로 넣을 수 있다, §12).
- 하늘: v1 배경 그림(`assets/bg/s01_village`)의 위쪽을 카메라를 따라다니는 먼 판(거리 9,000)으로 그린다 → 카메라가 돌거나 숙이면 달·성이 **회전만큼만** 움직여 가까운 벽과 시차가 생긴다.

## 3. 캔버스 겹치기 · 해상도

게임 캔버스 `#screen` 은 `getContext('2d', {alpha:false})` 라 **그 아래에 GL 캔버스를 깔 수 없다**. 그래서 두 가지를 다 만들고 스스로 고르게 했다 (`?v2layer=0|1` 로 고정 가능):

| 방식 | 하는 일 | 좋은 점 | 나쁜 점 |
|---|---|---|---|
| **blit** (기본) | GL 캔버스는 DOM 에 붙이지 않고 매 프레임 `ctx.drawImage(glCanvas)` 로 게임 캔버스에 옮긴다 | v1 의 HUD·토스트·페이드·번쩍임·비네트·일시정지·QA 도구가 **아무 수정 없이** 그 위에 온다. DOM 캔버스 수가 늘지 않는다 | 화면 전체 복사 1회. 2D 캔버스가 GPU 가속이면 GPU 안 복사(싸다), **소프트웨어면 ReadPixels 로 돌아 매우 느리다**(헤드리스: 36–57 ms) |
| **layer** | GL 캔버스(`#v2b-gl`, z 1)와 HUD 용 투명 2D 캔버스(`#v2b-hud`, z 2)를 `#screen` 위·가상 패드(`#tpad`, z 10) 아래에 얹는다. 위치·크기는 매 프레임 `#screen` 의 상자를 따라간다 | 복사 0 (브라우저 합성기가 바로 올린다) | 게임이 `#screen` 에 그리는 것(토스트·페이드·번쩍임)은 가려진다 → 비네트는 HUD 캔버스에 다시 그렸다. 다른 장면이 위에 오면 숨긴다(200 ms 감시) |

- 자동 선택: blit 로 시작하고 `drawImage` 시간이 45프레임 평균 6 ms 를 넘으면 layer 로 바꾼다(한 방향). 헤드리스는 늘 layer 로 넘어간다. 지금 방식은 화면 맨 아래 작은 정보 줄(`B · WebGL2 · blit|layer · fps …`)에 나오고, **그 줄을 누르면 방식이 바뀐다**(폴드에서 바로 비교). `window.__v2.stats.mode` · `__v2.setLayer(bool)` 도 같다(§10 위험 1).
- 크기: GL 캔버스 = 게임 캔버스의 백킹 크기 × `resK`. 따라서 v1 의 품질 등급·DPR 상한·픽셀 예산을 그대로 따른다(폴드 medium: 1455×1100, high: 2000×1512 근처). `resK`(1 → 0.6)는 이 장면의 작은 조절기: 프레임 간격 평균이 22 ms 를 3초 넘으면 GL 해상도만 14 % 씩 줄이고(HUD 는 선명한 그대로), 17.6 ms 아래(60 Hz 수직 동기 포함)로 12초면 올린다(두 번까지).
- 안전 영역: HUD 는 `game.safe` 만큼 들여 그린다. GL 은 화면 전체(카메라는 안전 영역과 무관).
- 나갈 때(`exit`): GL 텍스처·버퍼·프로그램 삭제 + `WEBGL_lose_context` 로 컨텍스트 반납, 만든 캔버스 9–10개를 1×1 로 줄이고 DOM 에서 뗀다. `window.__v2` 삭제.
- 컨텍스트를 잃으면(`webglcontextlost`) `preventDefault` 후 "화면을 되살리는 중…" 을 띄우고, `webglcontextrestored` 에 셰이더·버퍼·텍스처를 원본 캔버스에서 다시 올린다(검사: 잃기 → 1.3초 뒤 다시 그림).
- WebGL 이 없으면 안내 문구만 띄우고 끝(예외 없음, 뒤로 = 타이틀).

## 4. 빌보드 방식과 가림 — 방식 (1) 을 골랐다

**퍼펫을 2D 캔버스(아틀라스)에 그려 텍스처로 올린다.** 이유:

1. **가림이 공짜로 정확하다.** 캐릭터가 GL 안의 사각형이므로 깊이 버퍼가 기둥·벽·단상·계단과의 앞뒤를 픽셀 단위로 푼다. 방식 (2)(2D 캔버스에 캐릭터를 그리고 가리는 물체를 다시 덧그리기)는 가리는 물체마다 예외 코드가 필요하고, 비스듬한 벽·계단에서 틀린다.
2. **세계의 빛·안개가 캐릭터에 같이 먹는다.** 멀리 있는 적은 안개에 묻히고, 가로등 밑에서는 따뜻하게 밝아진다(정점 색 한 번). 2D 덧그림으로는 따로 흉내 내야 한다.
3. **v1 그림 코드를 그대로 쓴다.** `chars.js` 는 v1 이 읽는 모양의 객체(`{cx:0, bottom:0, facing, anim, animT, move, moveT, …}`)를 만들어 `drawHero(ctx, p, null, {main:true})` · `drawEnemy(ctx, e, null)` 를 부를 뿐이다. 검 궤적·맞을 때 흰 번쩍임·마법진 같은 퍼펫 안의 효과도 그대로 따라온다. 어댑터는 약 60줄, 붙이는 데 걸린 시간은 20분 안쪽.
4. **비용이 작고 예측된다.** 퍼펫을 그리는 비용은 v1 과 같고(어차피 매 프레임 그리던 것), 더해지는 것은 아틀라스 텍스처 올리기 1회뿐.

- 아틀라스: 1024×1536(배율 ≤ 1.5) 또는 2048×2048(배율 2). 영웅 칸 340×256, 적 칸 210×180 논리 px(검 궤적 포함), 배율 = 게임 캔버스 배율(1–2, 0.25 단계). 화면에 보이는 캐릭터만 칸을 받고(선반 채우기), `texSubImage2D` 로 **쓴 줄만** 올린다(WebGL1 은 통째로).
- 세우는 법: 캐릭터 판은 **세계 x 축에 나란히** 세운다(카메라를 따라 돌지 않는다). 공격이 x 축 방향이고 판정이 z 차이를 보는 규칙과 그림이 일치하고, 길 건너 벽(같은 z)과 서로 파고들지 않는다. 요 20° 에서 폭이 6 % 좁아 보이는 것이 전부. 내려다보는 각 때문에 납작해 보이는 만큼 높이를 `1/cos(pitch)` 로 키운다.
- 그리는 순서: 하늘(깊이 끔) → 세계 메시(불투명, 깊이 씀) → 땅 스티커(그림자·예고 표시·창; 깊이 시험, 6 단위 당김) → **뷰 깊이로 정렬한 빌보드**(소품·캐릭터·빛·효과; 깊이 시험만, 쓰지 않음). 텍스처가 바뀌는 곳에서만 묶음을 끊는다.
- 미리 곱한 알파 하나로 보통 그림과 더하기 빛을 같은 묶음에 넣는다(정점의 '섞기' 값 0 = 더하기).
- **한계**: (a) 판끼리는 정렬로만 앞뒤를 정하므로 두 캐릭터가 같은 z 에서 겹치면 한쪽이 통째로 앞에 온다(2D 게임과 같다). (b) 판이 세로 벽(x 가 일정한 벽)을 넘어가면 칼끝이 벽에 잘린다 — 몸통 반지름만큼은 벽에서 떨어져 있어 드물다. (c) v1 적 그림이 발밑에 직접 그리는 납작한 그림자는 판에 붙어 선 채로 보인다(작아서 거의 안 보이지만, 정식판에서는 끄는 스위치가 필요 — §11 요청 2). (d) 퍼펫은 옆모습뿐이라 골목에서 화면 안쪽으로 걸어갈 때도 옆을 본 채 걷는다(§7).

## 5. 충돌

- 수평: 축별로 따로 움직이고 상자에 막히면 그 축만 멈춘다(벽을 따라 미끄러진다). 발보다 18 이하로 높은 턱은 그냥 오른다(계단), 20 이하로 낮으면 걸어 내려가고 더 낮으면 떨어진다.
- 수직: `groundAt(x, z, 발+18)` = 발밑에서 가장 높은 밟는 면. 없으면(-∞) 구덩이 → y < −170 에서 마지막 안전한 자리(가장자리에서 30 안쪽)로 돌아오고 체력 −8.
- 적: 같은 함수 + 낭떠러지 앞에서는 그 축으로 가지 않는다. 적끼리는 38 안에서 서로 민다.
- 상자 74개를 그냥 다 본다(영웅 1 + 적 16 → 프레임당 수천 번 비교, 측정 불가 수준). 장이 커지면 격자 색인을 넣는다.

## 6. 전투 판정 (부피)

- 영웅 공격: v1 `MOVESETS.sword.ground[0..2]`(3연타)·`air[0]` 의 상자(x·y)와 시간(`hit`, `cancel`, `hitstop`, `kb`, `lunge`)을 그대로 쓰고, **깊이 조건 |Δz| ≤ 28** 을 더했다. 높이는 상자의 y 범위로 본다(단상 위의 적은 아래에서 안 맞는다).
- 깊이 맞춰 주기: 공격을 시작할 때 앞쪽 170 안·|Δz| ≤ 64 안의 적이 있으면 첫 0.14초 동안 영웅의 z 를 그 적 쪽으로 끌어 준다(터치에서 깊이를 정확히 맞추기 어렵기 때문 — 손맛에 가장 크게 듣는 장치).

## 7. 입체감 — 쓴 것과 한계

쓴 것:
1. **진짜 원근**: 가까운 것이 크고 먼 것이 작다(거리 구간 앞뒤 가장자리에서 크기 차 약 1.3배). 평행선이 소실점으로 모인다(골목).
2. **시차**: 카메라가 움직이면 가까운 가로등·기둥과 먼 벽·하늘이 다른 속도로 움직인다. 공짜로 정확하다.
3. **카메라 요·기울기 전환**: 거리(비스듬한 옆모습) → 모퉁이에서 회전 → 골목(낮게 뒤에서) → 마당(높이 올라가 내려다봄, 영웅을 따라 돌아봄).
4. **거리 안개**: 760–3,300 에서 안개 색으로. 캐릭터·소품에도 같이.
5. **구운 빛**: 달빛 방향광으로 윗면·앞면·옆면 밝기가 다르고, 가로등·창·화로가 바닥과 벽에 따뜻한 웅덩이를 만든다. 벽 밑동·구덩이 속은 어둡다.
6. **그림자**: 캐릭터·소품·탄 밑의 둥근 그림자(높이 뜰수록 작고 옅게, 계단·단상 윗면에 떨어진다).
7. **깊이가 맞는 가림**: 기둥·가로등 뒤로 지나가면 가려지고 앞으로 지나가면 가린다. 단상 뒤, 계단 옆도 같다.
8. 구덩이는 진짜 구멍(어두운 돌벽), 길 가장자리는 옹벽, 골목 위 아치, 마당의 화로·석상.

한계 (솔직히):
- **캐릭터는 납작하다.** 옆모습 퍼펫 한 장이라 카메라가 돌아도 캐릭터는 돌지 않는다. 골목(종 구간)에서 안쪽으로 걸을 때 옆을 본 채 걷는 것이 가장 눈에 띄는 어색함이다(옛 벨트스크롤 게임과 같은 약속이지만 카메라가 뒤에 있어 더 눈에 띈다). v1 에는 카엘의 8방향 서 있는 그림(`drawHero(…, {yaw})`)이 있지만 **서 있을 때만** 쓰이고 달리기·공격은 옆모습뿐이라 시범판에서는 쓰지 않았다. 정식판에서는 앞·뒤로 달리는 그림이 필요하다 — A 방식도 똑같이 겪는 문제이고, B 는 방향별 그림만 있으면 판에 바꿔 끼우면 된다.
- 세계가 아직 **상자 위주**다. 맞배지붕(경사면·박공·처마)만 넣어 봤고 창틀·난간·굴뚝·문 같은 실루엣은 없다. 저폴리 조각이나 벽에 붙이는 그림(창·문·현수막은 이미 그렇게 했다)으로 채워야 한다.
- 텍스처가 v1 타일(512²) 재사용이라 가까이서 흐리다. 빛은 구운 것이라 움직이는 빛(탄, 화로 깜빡임)이 바닥을 비추지 않는다(빛 번짐 그림만 깜빡인다). 그림자는 둥근 얼룩이지 실루엣이 아니다.
- 안티에일리어싱을 껐다(성능 우선). 메시 가장자리에 계단이 보일 수 있다 — 기기에서 여유가 확인되면 MSAA 를 켠다.

## 10. WebView · 기기 위험

1. **겹치기 방식의 실제 비용을 모른다 (가장 큰 미지수).** 폴드의 WebView 에서 2D 캔버스가 GPU 가속이면 blit 가 싸지만, 아니면 프레임마다 화면 전체 ReadPixels 가 된다. 자동 전환(§3)을 넣었지만 임계값(6 ms)은 추정이다. → 폴드에서 `?v2layer=0` 과 `?v2layer=1` 을 둘 다 해 보고 `__v2.stats` 를 본다. 정식으로 가면 셸을 한 줄 고쳐(§11 요청 1) GL 을 `#screen` 아래에 까는 것이 가장 깨끗하다.
2. **컨텍스트 손실**: 안드로이드는 앱이 뒤로 갔다 오거나 메모리가 모자라면 GL 컨텍스트를 뺏는다. 복구 경로를 넣고 검사했지만(강제 손실), 실제 기기의 "뒤로 갔다 오기"는 직접 확인해야 한다.
3. **메모리**: 텍스처 21–31 MB + 캔버스 원본. v1 의 채색 텍스처 예산(휴대폰 32 MB/태블릿 40 MB)과 **따로** 든다. 지금은 `assets.track` 에 넣지 않았다(예산 밖) → 정식판에서는 넣어야 한다.
4. **아틀라스 올리기**: 2D 캔버스 → GL 텍스처는 크롬에서 GPU 안 복사가 되는 것이 보통이지만, 아닐 경우 프레임마다 3–5 MB 를 CPU 로 올린다(헤드리스 0.82 MP 에 5–7 ms; 실제 기기는 대개 1 ms 안팎으로 예상하나 **재지 않았다**). 대책: 먼 적은 반 해상도 칸, 서 있는 적은 2–3프레임에 한 번만 갱신, 칸을 캐릭터별 고정 자리로 두고 바뀐 칸만 올리기.
5. **절전·저사양**: v1 품질 조절기는 이 장면을 재지 않는다(`GOV_SCENES` 에 없음) → 장면 안의 `resK` 조절기로 대신했다. 정식판에서는 셸의 조절기에 GL 장면을 넣는다.
6. WebGL2 는 안드로이드 WebView 58+ 에서 된다. 안 되면 WebGL1 로 내려간다(셰이더는 GLSL ES 1.00 만 쓴다). `?v2gl=1` 로 WebGL1 을 강제해 헤드리스에서 같은 화면이 나오는 것을 확인했다.
7. CSP: 인라인 스크립트·스타일 속성 없음(스타일은 CSSOM 으로만). 외부 주소 없음. 번들 검사 결과는 §8.

## 12. 스테이지 한 장의 제작 비용 · 60장 이상으로

저작(데이터):
- 시범 구간(횡 2,400 + 종 1,300 + 마당)은 **part 84줄 + 구간 4 + 적 16** 이다. 손으로 쓰고 캡처로 확인하며 다듬는 데 약 1.5시간 걸렸다(형식을 만드는 시간 제외). 익숙해지면 같은 크기의 장 하나에 1–2시간, 방 5–6개짜리 한 장에 하루.
- 빨리 찍어내려면: ① **미리 만든 덩어리**(집 한 채 = 벽+창+지붕, 계단 달린 단상, 골목 한 토막, 마당 틀)를 함수로 두고 줄 수를 1/3 로 ② 위에서 본 격자 편집기(상자를 끌어 놓고 높이를 적는 도구; 형식이 단순해 2–3일이면 만든다) ③ `validateStage` 를 저작 도구와 CI 에 물린다 ④ 카메라 틀은 구간 종류별 기본값(횡/종/광장)을 쓰고 필요한 곳만 덮어쓴다.
- 검증에 더할 것: 카메라와 놀이 공간 사이의 높은 벽, 소품이 길을 막는지(폭 < 60), 적이 벽 속에 있는지(지금 있음), 구덩이 건너편이 닿는지(지금 있음), 빛이 너무 어두운 구역.

그림:
- **텍스처**: 장 분위기마다 바닥 2 + 벽 2 + 돌 1 = 512² 타일 5장 안팎. v1 타일이 20장 있어 초반 장은 재사용 + 색조 바꾸기로 버틴다. 새로 그리면 장당 5장(Higgsfield 타일은 이음매 손질 필요).
- **하늘**: 장당 1장(v1 배경 25장을 그대로 쓸 수 있다).
- **소품**: 빌보드 그림. v1 `assets/props` 약 90장을 그대로 쓴다. 새 장마다 5–10장.
- **건물 실루엣**: 지금 가장 모자란 부분. 지붕·아치·난간·문 같은 저폴리 조각 20–30종을 한 번 만들어 두면(코드로 생성: 상자·쐐기·8각 기둥) 모든 장이 돌려쓴다. 1–2주.
- **캐릭터**: 화면 방식과 무관한 비용(재디자인). 다만 B 는 방향별 그림이 있어야 종 구간이 자연스럽다 → 영웅은 앞·뒤·옆 3방향(좌우 뒤집기 포함 사실상 6–8방향), 적은 옆 + 앞 2방향이 현실적인 최소.

실행 비용이 장 크기에 어떻게 느는가: 삼각형은 장 넓이에 비례(이 구간 8,400). 방 단위로 메시를 나누고 보이는 방만 그리면 장이 커져도 프레임당 삼각형은 1–2만에 머문다. 텍스처는 분위기 묶음당 21 MB 로 일정.

## 13. 다음 단계 (B 로 간다면)

1. **폴드 실측**: blit/layer 비용, 아틀라스 올리기, 60 fps 유지 여부, 컨텍스트 손실 복구. 결과에 따라 셸 요청 1 을 넣는다.
2. 방향별 캐릭터 그림(앞·뒤) 1명 시험 → 종 구간의 어색함이 풀리는지 확인.
3. 건물 조각(지붕·아치·난간) 생성기 + 덩어리 함수 → 상자 티 벗기.
4. 방 단위 메시 분할·보이는 방만 그리기, 충돌 격자, 스프라이트 풀(할당 0).
5. 적 그림용 가짜 world(쓰러짐 조각·파티클)와 손맛 모듈(impact) 연결.
6. 격자 편집기 + 검증 CI.
7. 움직이는 빛 2–3개(영웅·탄·화로)만 셰이더에서 계산, MSAA 여부 결정.
