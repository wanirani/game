# 성능 메모 — 폴드에서 왜 끊기는가 (v2)

2026-11-17. 소유자가 폴드(Galaxy Z Fold 8, 펼친 화면, 안드로이드 WebView APK)에서 시범판을 해 보고 한 말: **"a는 일단 많이 끊겨. b도 끊기지만 a보다는 덜 끊김."**
우리는 그 기기를 만질 수 없다. 그래서 (1) 코드에서 의심 원인을 모두 찾아 순위를 매기고, (2) 기기가 스스로 재서 결과를 글로 돌려주는 **성능 진단 화면**을 만들었다. 이 문서는 둘을 묶은 것이다.

- 진단 화면: `index.html?scene=v2bench` · 코드 `src/v2/bench/` · 검사 `node tools/v2/bench_check.mjs`
- **아직 모르는 것:** 아래 순위는 코드와 계산으로 세운 **가설**이다. 폴드의 실제 숫자는 하나도 없다. 진단 결과가 오면 §2 의 순위를 고쳐 쓴다.
- 헤드리스 Chromium 의 WebGL 은 소프트웨어 렌더러(SwiftShader)다. 이 문서의 프레임 시간 숫자 가운데 "헤드리스"라고 적힌 것은 **기기의 속도가 아니다**.

## 0. 소유자가 할 일 (1분)

1. 진단 화면을 연다: 타이틀 → **리빌드 시범** → **성능 진단** (셋째 줄; 2026-11-17 검수 때 `src/v2/chooser.js` 에 넣었다 — 이 줄이 든 APK 부터 보인다. 개발 서버에서는 주소 `?scene=v2bench` 로도 열린다).
2. 화면을 건드리지 않고 약 1분 기다린다 (재는 동안에는 화면에 단추가 없다. 도중에 나오려면 기기의 뒤로 가기). 같은 길을 달리는 장면이 설정을 바꿔 가며 12–13번 나온다.
3. 결과 표가 나오면 **「결과 복사」** 를 누르고, 복사된 글을 그대로 붙여 보낸다. (복사가 안 되는 기기에서는 글 상자가 뜬다 — 길게 눌러 전체 선택 → 복사.)
4. **「이 설정으로 하기」** 를 누르면 가장 부드러웠던 설정이 기기에 저장된다 (시범판이 이 값을 읽게 하는 일은 요청 중 — §5).
5. 여유가 있으면 한 번 더: 「다시 재기」를 누른 뒤 **손가락 하나를 화면 구석에 댄 채로** 기다린다. 손을 대고 있을 때 기기가 주사율·속도를 올리는지 볼 수 있다 (복사한 글의 `touchEv` 가 0 이 아니면 그 실행이다).

### 원인 1 의 계산 (게임 루프 박자)

`node tools/v2/bench_check.mjs --no-devices` 가 `game.js` 의 누적기 식을 그대로 10분 분량 돌린 값이다. 그리는 시간은 0 으로 두었다 — **순수하게 박자만**의 문제다.

| 화면 | 시각 모형 | 초당 새 그림 | 고르지 않은 그림 | 간격(95 %) |
|---|---|---|---|---|
| 60 Hz | 화면이 시계보다 50–500 ppm 빠름 | 60 | 0.1–0.2 % | 16.7 ms |
| 60 Hz | 정확히 60 + 시각 0.1 ms 단위 | 40 | 50 % | 33.3 ms |
| 90 Hz | (어느 모형이든) | 60 | 50 % | 22.3 ms |
| **120 Hz** | 화면이 시계보다 50–500 ppm 빠름 | 60 | **0.4–0.6 %** | 16.7 ms (가끔 25) |
| **120 Hz** | 정확히 120 (시각이 정확하든 0.1 ms 단위든) | 60 | **66 %** | 25 ms |
| **120 Hz** | ±0.3 ms 흔들림 | 60 | **32 %** | 25 ms |
| 144 Hz | (어느 모형이든) | 60 | 40 % | 20.9 ms |

- 읽는 법: 120 Hz 에서 지금 루프는 **운이 좋으면 거의 고르고(0.5 %), 나쁘면 세 장 중 두 장이 어긋난다(66 %)**. 어느 쪽인지는 그 기기가 rAF 에 주는 시각이 얼마나 정확한가에 달려 있고, 코드로는 알 수 없다. 그래서 진단의 '초당 60' 줄이 이것을 직접 잰다.
- "매 화면 그리기 + 보간" 은 어느 모형에서도 0 % 다.
- 틀 검증: 같은 도구의 `--pace` 는 가짜 화면 시계를 페이지에 끼워 진단 장면을 통째로 돌린다. 결과는 §6 끝.

## 3. 진단 화면이 재는 것과 읽는 법

**무엇을 그리나:** 시범판 B 의 세계(SLICE0 거리 구간)를 초당 280 의 속도로 달리는 정해진 카메라 길(시험마다 같은 길을 처음부터). 영웅 + 들러리 12명이 늘 화면에 있다. 세계·렌더러·퍼펫·입체 모델은 `src/v2/b/`·`src/v2/char3d/` 의 것을 **읽기만** 해서 그대로 쓴다(그리는 순서·할당 방식도 `b/index.js` 를 따랐다).

**어떻게 재나:** 게임 루프는 고치지 않는다. '초당 60' 은 지금 그대로(틱이 돈 프레임만 그림), '매 화면' 은 장면이 `render()` 안에서 `game.dirty = true` 를 다시 걸어 모든 rAF 에 그리고 장면 시각을 rAF 시각으로 쓴다. 화면 간격은 따로 건 rAF 가 잰다. 시험 하나는 4초, 앞 1초는 버린다. 시험마다 끝에 5프레임은 `readPixels` 로 GL 을 끝까지 기다려 `glsync` 를 잰다.

- **초당 그림** — 실제로 새 그림이 올라간 횟수. **끊김** — 새 그림 간격이 그 시험의 보통 간격에서 35 % 넘게 벗어난 비율. 눈에 보이는 끊김에 가장 가깝다 (초당 60장으로 고르게 가는 것은 끊김이 아니다).
- **느린 화면** — 화면 간격이 주사율 간격의 1.5배를 넘은 비율. **화면 간격 보통/느릴 때 · 최장** — 중앙값 / 95 % / 가장 긴 멈춤(ms).
- **추천**(금색 줄) — 본편이 쓸 캐릭터 방식(입체) 줄 가운데: 끊김 등급(2 % 단위)이 낮은 것 → 초당 그림이 많은 것 → 해상도가 높은 것 → 겹쳐 얹기 → 매 화면. 50 % 해상도는 75 % 이상에서 부드러운 줄이 하나도 없을 때만 고른다. 흐린 줄은 참고용이라 추천되지 않는다.

## 7. 진단 화면 자체의 한계

- 놀이가 아니라 **정해진 길의 재생**이다. 전투 판정·적 AI·효과(불티·숫자)·터치 입력은 돌지 않는다. 시범판 B 가 잰 값으로는 그 부분의 스크립트 시간이 1 ms 안쪽이라 뺐다.
- GPU 시간은 직접 못 잰다(WebView 에 타이머 확장이 없다). `glsync` 가 그 대신이다. 2D 캔버스 쪽 GPU 일(복사·합성)은 `glsync` 에 안 들어가고, 화면 간격으로만 드러난다.
- 손을 대지 않은 상태로 잰다. 놀이 중에는 손가락이 늘 화면에 있다 → §0 의 5번.
- 가비지 수거는 브라우저가 알려 주는 힙 크기의 내림으로 센다(거친 값). 
- 시험 순서가 고정이라 기기가 달아오르면 뒤쪽 줄이 불리할 수 있다. 의심되면 「다시 재기」로 두 번 재서 견준다.
- **B 의 옛 세계(정적 삼각형 약 8,600)로만 잰다.** 꾸민 배경(`v2c`, 약 26,400 · 정점 버퍼 2.7배 · 텍스처 +7 MB)이 기기에서 얼마나 더 무거운지는 이 진단으로 알 수 없다 (검수 때 확인, §8).
- 가장 가벼운 시험도 주사율을 못 따라가는 기기에서는 주사율을 낮게 읽고(헤드리스에서는 바쁠 때 30 Hz 로 읽었다), 그러면 "끊김 %" 와 추천이 뜻을 잃는다. 복사한 글의 `fastest5%` 를 같이 본다.

- 그리기(`render`)에서 예외가 나도 멈추지는 않는다: 시험은 따로 건 rAF 고리의 시각으로 넘어가고, 게임 루프는 다음 rAF 를 먼저 건다(코드로 확인).
